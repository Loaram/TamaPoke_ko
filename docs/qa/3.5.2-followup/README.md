# 3.5.2 후속 수정·재시뮬레이션 보고서

기준: 정식 3.5.2 (`e947337b8c08803b06ec2e7c3811ac5112f45f93`). 검사일: 2026-09-07.

**배포 전 로컬 수정본을 검사한 당시의 보고서**다. 검사 당시 버전 번호·공개 릴리스·설치 페이지는 변경하지 않았으며 실제 사용자 세이브나 기기에 적용하지 않았다. 이후 이 수정사항을 [3.5.3 버그 패치](../../RELEASE-3.5.3.ko.md)로 묶었다. 버전별 배포 검증은 [3.5.3 기록](../3.5.3/README.md)을 참고한다.

## 수정 전후

| 문제 | 수정 전 | 수정 후 재현 결과 |
|---|---|---|
| 구버전 미완료 교체 복구 + 날짜 경계를 넘는 시간대 변경 | 훈련 `22/33/44 → 12/23/34` | `22/33/44` 유지, 재시작 후에도 유지 |
| 복구 대기 중 재시작·오프라인 처리 | 성장 `1,180 → 1,240분`, 복구 후 다시 1,180분 | 복구 중 1,180분 유지, 성공 후 새로 지난 1분만 반영 |
| 파티 놓아주기 확인창에서 스와이프 후 다른 개체 선택 | 이전 확인 상태가 다른 개체로 넘어감 | 확인 상태 취소, 새 개체는 일반 상세창 표시 |
| 저장 불가 상태에서 탐색 시작 | 시작됨, 활력 `100 → 70` | 시작 거부, 활력 100 유지, 저장 상태 안내 표시 |
| 트레이너 이름 변경 첫 키 입력 | 첫 A 입력 누락 | 첫 입력 즉시 TESTA, 두 번 입력하면 TESTAA |

## 구현 범위

- `Pet::readStoredSnapshot()`이 저장 당시 날짜로 개체를 재구성한 뒤 전체 기록을 대조한다. 시간대에 따라 바뀌는 현재 날짜를 부분 저장의 증거로 취급하지 않는다. 개체값·훈련·기술·성장 등 실제 저장 항목의 불일치 검사는 그대로 유지한다.
- 교체 복구가 미완료이면 시작 시 오프라인 진행과 Android pause/resume/checkpoint 저장을 차단한다. 재시도 성공 후 시계 기준을 다시 잡아 대기 시간을 한꺼번에 진행하지 않는다.
- 파티 상세창을 스와이프로 닫거나 새 개체를 선택하면 놓아주기 확인 상태를 지운다.
- 탐색 시작과 버튼 활성화에 저장 가능 여부를 반영한다. 읽기 전용·교체 복구·거래 잠금 상태에서는 난수 추첨과 활력 소모 전에 거부한다.
- 키보드 입력이 뒤쪽 트레이너 화면보다 먼저 처리된다. 키보드가 열린 동안 스와이프가 뒤쪽 페이지를 변경하지 않으며, 이름 확정 후 트레이너 화면으로 돌아간다.
- 저장 v7, 개체 72바이트, 보관 300칸, 전송 및 대전 프로토콜, 데이터 번호와 밸런스는 변경하지 않았다.

## 재검증

**전체 런타임 58개 검사 통과.** 이전 수정 전 실행에서 Windows 보안 정책으로 차단됐던 i18n 검사도 이번 수정본에서는 실행되어 통과했다. 보안 설정은 변경하지 않았다. 새 시뮬레이션의 미해결 재현 오류는 0건이다.

추가 시뮬레이션은 다음과 같이 통과했다.

- **저장 중단 1,056건:** 알/살아 있는 개체, 수면 여부, 높은 기존 훈련값, 파티/박스 끝 칸을 조합했다. 각 저장 경계에서 다시 시작하고 두 번째 재시작까지 확인했다. 개체 유실·예상 밖 복구 잠금·개체값/훈련/이로치/폼 불일치 모두 0건.
- **연속 교체·훈련·정렬·재시작 1,200회:** 개체 보존 및 훈련 저장 오류 0건.
- **통신 장애 조합 90건:** 두 가상 기기 사이에 20~33% 패킷 유실, 중복, 순서 변경과 조합당 재부팅 3회를 섞어 전송·교환을 완료했다. 오류 0건.
- **시간대 대조군:** 변경 없음, +1시간, -9시간, +9시간을 원래 재현 시나리오로 확인했다. 새 회귀 검사는 ±24시간 조건도 포함한다.
- **부분 저장 방어:** 날짜 처리 수정 뒤에도 개체값·훈련·기술·이름·성장·수면 등 12개 실제 저장 항목이 달라진 기록은 정상 저장으로 인정하지 않는다.
- **SD 저장 장애 10개**, 한글 문자열/글꼴, 폼 데이터 검사 통과.
- **빌드:** PC 에뮬레이터, Android ARM64/x86_64, Wear OS ARM32/ARM64, ESP32-S3 성공. ESP 앱 바이너리 2,277,616바이트.
- 새 `recovery_clock`, `modal_safety` 검사를 기존 자동 검사 목록에 추가했다. 기존 복구·전체 저장·개별 전송·대전·성장 검사도 재실행하여 통과했다.

## 증거와 재실행

수정 전 증거는 `build/diagnostics/352-simulation/`에 보존하고, 수정 후 증거는 별도 `build/diagnostics/352-fixed/`에 저장했다.

- `core.log`: 1,056개 저장 중단, 1,200회 교체, 복구 중 시계, 시간대 변경 결과.
- `ui.log`, PNG 화면: 이름 첫 입력·놓아주기·저장 불가 탐색의 수정 전후 확인.
- `network.log`: 90개 장애 조합.
- `runtime-all.log`: 전체 회귀 검사.
- `sd.log`, `korean.log`, `forms.log`: 추가 검증.
- `android-build.log`, `wear-build.log`, `esp-build.log`: 기기별 로컬 빌드.
- `verification.json`: 완료된 검증 결과와 소스/검수용 빌드 SHA-256 기록.

일반 회귀 검사는 `tools/build_emulator.py`로 스케치를 생성한 뒤 `tools/test_runtime.py`로 재실행한다. 새 검사만 실행하려면 `--only recovery_clock,modal_safety,swap_recovery,android_lifecycle`을 사용할 수 있다.

## 한계와 배포 상태

시뮬레이션은 실제 게임 코드를 사용하지만 물리 기기의 전원 차단·실제 Wi-Fi/ESP-NOW·휴대전화와 워치의 설치 시험을 대신하지 않는다. 저장 항목 경계 주입은 공통 복구 로직을 검사하며, 모든 경계가 Android의 실제 파일 저장 시점과 같다는 뜻은 아니다.

이 시뮬레이션 작업 당시에는 업로드하거나 설치하지 않았다. 검수용 APK와 ESP 바이너리는 별도 로컬 폴더에 보존하며 기존 공개 3.5.2 파일을 교체하지 않는다. 후속 3.5.3 배포에서는 번호를 적용해 모든 배포 자산과 가이드를 다시 생성한다.
