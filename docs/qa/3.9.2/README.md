# 3.9.2 교체 저장 안정화 검증

## 보고와 원인 판단의 한계

원형 ESP에서 히드런 → 무한다이노(무한다이맥스) → 탐색 → 포획 → 히드런으로 돌아올 때 교체 저장 보호창에 멈춘다는 보고다. 다시 확인은 해결하지 못하고 재부팅하면 정상화된다. 사용자는 원격 환경이어서 USB 로그를 제공할 수 없다.

기존 코드에서도 정상 메모리의 해당 순서는 통과했다. 따라서 폼 자체의 기록 손상이나 실제 기기의 유일한 원인을 확정하지 않는다. 대신 ESP SD 검증의 추가 대형 메모리 할당을 실패시키면 기존 코드가 실패하고 수정 코드가 통과함을 확인했다. 이 결과는 메모리 부담에 대한 수정 근거이지 실물 원인 확정이나 실기 해결 완료 증거는 아니다.

## 수정

- 22,116바이트 저장 원본은 유지하고, 동시에 존재하던 같은 크기 검증 버퍼 2개를 제거했다. ESP는 256바이트씩 전체 파일을 비교한다.
- 파일 길이, 모든 바이트, 해시, 원자 저장 선택자와 이전 복구본 보호는 그대로 검사한다.
- 교체/재시도 전에 현재·진화·도감·배틀 그림 캐시를 해제한다. 세이브 데이터는 해제하지 않는다.
- 아직 교체 보호 중이면 데려오기를 성공으로 처리하지 않는다.
- 세이브 v7, 72바이트 개체 기록, SD 파일 형식, 파티션, 통신과 밸런스는 그대로다.

## 검증 목록

- shared_energy: 실제 탐색·성공 포획 경로 포함. 히드런485/무한다이노890·폼10359, 양방향, 파티/박스299번 인덱스, 레벨100·동일31IV·비영 돌봄 기록으로 복귀 비교. 공용 활력만 탐색 비용22 감소.
- swap_recovery / active_swap: 저장 중단·재시도·재부팅·훈련 보존·애매한 이전 저장 보호.
- SD fault injection: 추가 1KiB 초과 할당 불가, 첫/255/256/마지막 바이트 손상, 짧은 읽기/쓰기, 저장 선택자 실패, 잘못된 카드 및 누락. 실패 시 이전 스냅샷을 선택한다.
- 전체 런타임67종, Android 네트워크 콜백20개, SD 업로드30개, 웹 설치 회귀, Windows 워치 도우미30개.
- Android3056/Wear3057 서명·ABI·그림 팩, ESP NVS 안전 주소, 배포9자산 전체 해시와 ZIP 검사.
- 플레이31쪽·워치 도우미7쪽을 전부 렌더링하여 육안 검사. 기존 수동 설치PDF도 그대로 동봉.

각 완료 결과는 동봉 로그와 build-results.json에 기록한다. 공개 전 최종 커밋의 Verify Korean edition 성공을 확인하며 공개 후 릴리스·태그·main·Pages의 해시를 검증한다.

첫 서버 검사에서는 전체67종과 Java20개가 통과한 뒤 SD 시험의 malloc 실패 주입 매크로가 GCC의 stdlib.h 래퍼와 충돌해 시험 컴파일이 실패했다. 시험 파일에서 표준 헤더를 먼저 포함하도록 수정했다. 게임/펌웨어 소스 및 배포 바이너리는 이 후속 수정으로 바뀌지 않는다. 마지막 커밋에서 전체 서버 검사를 다시 실행한다.

## 실기 후속 확인

이번 기기에 설치하거나 저장을 초기화하지 않았다. 업데이트 전 백업하고 기존 SD를 유지한다. 같은 교체/탐색/포획 순서를 반복하고 보호창이 나타나면 다시 확인을 시험한다. 지속되면 초기화하지 말고 발생 순서 및 저장 공간/카드 상태를 추가 조사한다. 실제 프레임속도, SD 전원 차단, 기기 해결 여부는 아직 미검증이다.
